## 0. 方針

設計検討(§0〜§16)から導かれた、実装順序を決める 5 つの判断。

| # | 判断 | 根拠 |
|---|---|---|
| 1 | **発報も検知も Watch 側に置く。** iPhone は「ペリフェラル役」と「位置の事前送信役」 | §1 |
| 2 | **距離判定の主役は GPS ではなく歩行距離(`CMPedometer`)**。方式2(GPS)は後回しでよい | §14.1、§14.7 |
| 3 | **「止めるまで鳴る」を最優先で作る。** これが満たせなければアプリの存在意義が無い | §7、§9-6 |
| 4 | **背景での検知が成立するかは、実機でしか分からない。** 早い段階で実機スパイクを打つ | §10-1、§10-2 |
| 5 | **コンプリケーションは飾りではなく前提条件。** 無いと背景更新が 1 時間に 1 回まで落ちる | §14.10 |

この結果、**「既存バグの修正 → 鳴り続けるアラーム → 状態機械 → 遡及検出」の順に積む**。
GPS(方式2)とサーバ(Tier 1)は任意の枝として最後に置く。

> **2026-09-01 の変更**: 手元の実機が **Apple Watch SE(第1世代)** と判明し、
> 背景 BLE 起床の要件「Series 6 以降」を満たさないことが分かった(詳細は
> [docs/spike-g0.md](spike-g0.md) §2.6)。**G0-1 / G0-2 は Series 6 以降の実機が入るまで測定できない。**
> 一方 **P1 は背景 BLE 起床を使わないため、現在の機体で実機検証まで完了できる。**
> よって **G0 の完了を待たず P1 を先に進め、あわせて G0-3 だけ現在の機体で測る**方針に変更した。
> G0-1 / G0-2 は保留のまま残す(P2 の設計に必要なので破棄はしない)。

> **2026-09-02 の追記**: BLE の実効レンジ・背景実行能力・切断検知の可否を追加調査した
> (設計 §17 / §18 / §19)。実装計画に効く点は次の 4 つ。
>
> 1. **ペリフェラル役の iPhone は切断を検知できない**(§19.3)。P4 の設計前提に影響する。
> 2. **切断時刻が取れる API**(`didDisconnectPeripheral:timestamp:`、watchOS 10+)がある(§19.5-2)。
>    P3 の遡及判定の基準時刻はこれを使う。→ P0-9 を追加。
> 3. **`registerForConnectionEvents` は watchOS 6.0+ で使える**(§19.5-4)。
>    背景 BLE 起床とは別系統なので、**Series 6 未満の現在の機体でも試せる可能性がある。**
>    → G0-5 を追加。**保留中の G0-1 / G0-2 を迂回できるかもしれない、今いちばん価値の高い検証。**
> 4. **AlarmKit(iOS 26+)** で、Critical Alerts の個別申請なしに消音貫通アラームが作れる(§18.4)。
>    watchOS SDK が無いので本線には効かないが、**P4 の盗難検知にはそのまま使える。**

### 全体構成

```
G0 実機スパイク ──▶ P0 地固め ──▶ P1 鳴り続ける ──▶ P2 状態機械 ──▶ P3 遡及検出 ──▶ G1 検証
  └ G0-1/G0-2 は保留(要 Series 6+)      ↑
  └ G0-3 は現機体で測定可能              └ 先に着手する
                                                                              │
                                                                              ├─▶ P4 iPhone コンパニオン(盗難検知)
                                                                              ├┄▶ P5 GPS 距離 (任意)
                                                                              ├┄▶ P6 サーバ中継 (任意)
                                                                              └┄▶ P7 モーション付きタグ (任意)
```

### 前提条件(満たせないと成立しない)

| 条件 | 理由 |
|---|---|
| **Apple Watch Series 6 以降 + watchOS 9 以降** | 背景 BLE 起床の動作要件(§2.1)。GPS 測位の機種差(§12.3-14)も同じ線で切れる |
| **実機での検証**(シミュレータ不可) | 背景 BLE / WatchConnectivity / CoreMotion はシミュレータで再現しない(§10-1) |
| **文字盤にコンプリケーションを置いてもらう** | 背景更新の予算がこれで決まる(§14.10) |
| iPhone 側は位置情報「常に許可」 | ジオフェンス盗難検知の前提(§15.3) |

## G0. 実機スパイク(最優先・使い捨て)

**目的:** 後続の設計を左右する未知を、実装前に潰す。

| # | 確かめること | 機体要件 | 外れたときの影響 |
|---|---|---|---|
| G0-1 | 背景 BLE 起床(`bluetooth-central` + notify)が実際に来るか | Series 6+ / **保留** | 来なければ方式1 が丸ごと成立しない。設計の作り直し |
| G0-2 | **5 回/24h の予算が `didDisconnect` 起床も数えるか**(§10-2) | Series 6+ / **保留** | 数えるなら §6 の予算管理を大幅に厳しくする必要がある |
| G0-3 | 背景起床 1 回の実行時間で `queryPedometerData` / `queryActivityStarting` が返るか(§14.4) | **現機体で可** | 返らなければ P3 の遡及検出が背景で使えず、前面専用に格下げ |
| **G0-4** | **切断起床で貰える「再接続用の短い枠」でローカル通知を積めるか**(§19.4 / §19.7-1) | Series 6+ / 保留 | 積めなければ方式1 は「再接続を試して黙る」だけになる。**方式1 の成否を分ける** |
| **G0-5** | **`registerForConnectionEvents` が watchOS の背景で発火するか**(§19.5-4) | **現機体で試せる可能性** | 発火すれば **Series 6 未満でも方式1 が成立する道**が開ける。保留中の G0-1 / G0-2 を迂回できる |

> **G0-5 を最優先で試す。** watchOS 6.0+ の API であり、背景 BLE 起床(Series 6 要件)とは別系統。
> 相手役は既存の `spike/peripheral-sim` で足りる。

**やり方:** 本体とは別の使い捨てターゲットでよい。ログを `UserDefaults` に貯めて前面で読む。
**完了条件:** 現機体で測れる項目(G0-3 / G0-5)の実測値が記録され、P2 / P3 の設計に反映されている。
G0-1 / G0-2 / G0-4 は Series 6 以降の機体が入るまで保留。

| **P0-10** | **`txPower` / `n` の実機較正。** 1m 刻みの RSSI を屋内・屋外で記録し、現在の `-59` / `2.0` を置き換える | `BLEManager` | §17.3 / §17.6 |

**完了条件**
- `performBackgroundRSSICheck()` の未接続分岐が実際に発火する(P0-2 の検証)

- アプリを背景で終了させ、再起動してもアラーム状態が復元される
- **切断イベントに「いつ切れたか」が付いている**(P0-9。P3 の遡及判定の前提)
- **距離しきい値が実測に基づいている**(P0-10。較正前の 2m は根拠を持たない、§17.3)

## P1. 止めるまで鳴るアラーム(§7)

**目的:** README が約束している「手動で停止するまで鳴り続ける」を実際に満たす。
現行実装は**画面が消えた瞬間に鳴り止む**(§9-6)。ここが製品の核。

| ID | 内容 | 対象 | 出典 |
|---|---|---|---|
| P1-1 | `UNNotificationCategory`(`TURETETTE_ALARM`)と「停止」アクションの登録 | `AlarmManager` | §2.4 |
| P1-2 | **通知の連投**(5 秒間隔 × 48 発、`threadIdentifier` で束ねる) | `AlarmManager` | §7 段階2 |
| P1-3 | **全 ID の一括キャンセル**(pending と delivered の両方) | `AlarmManager` | §7 |
| P1-4 | `interruptionLevel = .timeSensitive` + Time Sensitive capability | `AlarmManager` / entitlements | §2.4 |
| P1-5 | `WKExtendedRuntimeSession` でハプティクス継続 + `WKBackgroundModes` に適正値 | `AlarmManager` | §7 段階3 |
| P1-6 | 背景終了 → 前面化でのアラーム継続 | `AlarmManager` | §9-7 |
| P1-7 | 停止導線と状態表示の整理 | `Views/AlarmView` | ― |
| P1-8 | (任意)Critical Alerts entitlement の申請 | ― | §7 段階0 |

**注意**
- `start()` は**前面でしか呼べない**(§2.3)。段階3 は「ユーザが通知をタップしてアプリが前面に来た後」に限る
- セッション種別は用途との整合に審査リスクがある(§10-3)。`physical-therapy` を第一候補に、指摘されたら再検討
- 未配信通知は 64 件上限(§2.4)。48 発は余裕を残した数

**完了条件**
- 画面を消したまま 4 分以上鳴り続ける
- 「停止」を押すと**通知センターに 1 件も残らない**
- 通知タップ → 前面化 → 停止するまで無限にハプティクスが続く

**目的:** 設計上いちばん効く部分。GPS を使わずに「離れた」を判定する。

|---|---|---|---|

| P3-3 | **`retrospectiveCheck` 決定表**(歩行距離 L・乗り物 V・連続歩行 C・階 F) | `MotionManager` / `ProximityCoordinator` | §14.5 |
| P3-4 | `longestContinuousWalk`(連続歩行時間の算出) | `MotionManager` | §14.6 |
| P3-5 | 監視レベル L0 / L1 / L2 と、レベル依存の猶予・進行中猶予の短縮 | `ProximityCoordinator` | §13.2、§13.8 |
| P3-6 | 保留切断イベント(TTL 30 分)と遅延発報 | `ProximityCoordinator` | §13.8 |
| P3-7 | BAR の適応スケジューリングと再予約 | `AppDelegate` | §13.6、§14.10 |
| P3-8 | **コンプリケーションの提供**と「文字盤に追加してください」のオンボーディング | 新規 `Complications` / `Views` | §14.10 ★ |
| P3-9 | `isDistanceAvailable` / `isFloorCountingAvailable` による機能縮退 | `MotionManager` | §14.8-5 |
| P3-10 | 設定「静止中も鳴らす」 | `Views/` | §13.8 |
| P3-11 | (任意)`HKObserverQuery` + 背景配信で歩数起床 | 新規 `HealthKitManager` | §14.9 |

**判定の核(§14.5)** ── 上から評価し、最初に当たったものを採る。

| # | 条件 | 判定 |
|---|---|---|
| 1 | 歩数データが取れない(権限なし / 未対応) | 判定不能 → 方式1 に従う(= 鳴る) |
| 2 | 乗り物で移動した | 発報(強) |
| 3 | 経路長 ≧ 150m **かつ** 連続歩行 ≧ 60 秒 | 発報(強) |
| 4 | 階移動あり かつ 経路長 ≧ 40m | 発報(中) |
| 5 | 経路長 < 30m | **抑制**(経路長は変位の上界なので確実に近い) |
| 6 | 上記以外 | 弱い通知 1 発のみ |

**完了条件**
- 机に iPhone を置いて席を立つ → 鳴る(遅延発報を含む)
- 同じ部屋の中を 5 分歩き回る → 鳴らない(#5 または #3 の連続歩行条件で抑制)
- Motion & Fitness を拒否した状態でも、見逃しが増えない(#1 が「鳴る」側に倒れる)

## P6. サーバ中継 ── Tier 1(任意)(§11)

**目的:** 圏内にいるときだけ効く冗長系。**ローカル完結版を置き換えない。**

| ID | 内容 |
|---|---|
| P6-1 | Watch アプリの独立 APNs 登録(`apns-topic` = watch アプリの bundle ID) |
| P6-2 | `AppDelegate.handle(_:)` に `WKURLSessionRefreshBackgroundTask` 分岐を追加 |
| P6-3 | iPhone: 大幅位置変更で起床 → background `URLSession` でサーバへ位置送信 |
| P6-4 | サーバ: 距離判定と **alert** push の送出(`background` 型は配信保証が無い、§10-11) |
| P6-5 | 二重発報の dedupe(イベント ID)と停止のサーバ同期 |
| P6-6 | 同意 UI、保存期間、削除手段、プライバシーラベル、README 文言 |

> **セルラー限定機能にしないこと。** GPS モデルでも Wi-Fi 圏内なら同じ経路が使える(§11.4)。

## P7. モーション付き BLE タグ(任意)(§16.5)

**目的:** 置き忘れと盗難を、距離もしきい値も無しに区別する。

| ID | 内容 |
|---|---|
| P7-1 | タグ側の wake-on-motion 仕様策定(**立ち上がりで 1 回だけ notify**。連投は予算を焼く) |
| P7-2 | タグ × Watch の 2×2 判定(タグ静止 × 自分移動 = 置き忘れ / タグ移動 × 自分静止 = 盗難) |

> **AirTag は使えない**(識別子が約 15 分で回転し、追跡対象にできない。§16.2)。

## 2. 進捗の更新方法

[docs/roadmap.html](roadmap.html) の先頭にある `PLAN` 配列で状態を管理している。

1. 該当タスクの `s`(status)を書き換える ── `"todo"` / `"wip"` / `"done"` / `"skip"`
