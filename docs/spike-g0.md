## 0. 何を確かめるのか

後続フェーズの設計を左右する未知。**外れると P2 / P3 を作り直すことになります。**

| #        | 問い                                                                  | 機体要件                 | 外れたときの影響                                       |
| -------- | --------------------------------------------------------------------- | ------------------------ | ------------------------------------------------------ |
| G0-1     | 背景 BLE 起床（`bluetooth-central` + notify）が実際に来るか           | Series 6+ / **保留**     | 来なければ方式1 が丸ごと成立しない                     |
| G0-2     | 5 回/24h の予算が `didDisconnect` 起床も数えるか（設計 §10-2）        | Series 6+ / **保留**     | 数えるなら §6 の予算管理を大幅に厳しくする             |
| G0-3     | 背景起床 1 回の実行枠で歩数・活動の遡り問い合わせが返るか（§14.4）    | **現機体で可**           | 返らなければ P3 の遡及検出は前面専用に格下げ           |
| **G0-4** | 切断起床で貰える「再接続用の短い枠」でローカル通知を積めるか（§19.4） | Series 6+ / 保留         | 積めなければ方式1 は「再接続を試して黙る」だけになる   |
| **G0-5** | `registerForConnectionEvents` が背景で発火するか（§19.5-4）           | **現機体で試せる可能性** | 発火すれば Series 6 未満でも方式1 が成立する道が開ける |

> **2026-09-02 追記**: G0-4 / G0-5 は追加調査（設計 §19）で浮上した問いです。
> とくに **G0-5 は `watchos(6.0)` の API** で背景 BLE 起床（Series 6 要件）とは別系統のため、
> **手元の Apple Watch SE(第1世代) でも試せる可能性があります。**
> 保留中の G0-1 / G0-2 を迂回できるかもしれないので、**現時点で最も価値の高い計測**です。

## 2. 準備

### 2-1. Mac 側（ペリフェラル役）

```bash
cd spike/peripheral-sim && swift run PeripheralSim
```

初回は Bluetooth の許可を求められます。拒否された場合は
システム設定 → プライバシーとセキュリティ → Bluetooth でターミナルを許可してください。

対話コマンド:

| キー | 動作                           |
| ---- | ------------------------------ |
| `n`  | notify を即時 1 回送る         |
| `d`  | 接続を切る（フェーズ B 用）    |
| `i`  | 送信間隔を変更する             |
| `s`  | 送信状況（送信数・連番）を表示 |
| `q`  | 終了                           |

### 2-2. Watch 側

`Spike/SpikeLog.swift` の `SpikeConfig.enabled` が `true` であることを確認し、実機へインストールします。
**インストール手順は §2.5 を参照**（Apple Watch にはケーブルが無く、Wi-Fi 経由で入れます）。
起動すると本体ではなく計測画面が出ます。画面は 3 タブ（状態 / 集計 / ログ）。

初回起動時に **モーションと Bluetooth の許可**を求められるので、両方許可してください。
`CMMotionActivityManager.authorizationStatus()` が「許可」になっていることを
状態タブ下部で確認します。ここが「拒否」だと G0-3 が測れません。

## 2.5. Apple Watch へのインストール

Apple Watch には Mac と繋ぐケーブルがありません。**Xcode から Wi-Fi 経由で直接インストールします**
（watchOS 6 以降の独立アプリはこれが正規の方法）。iPhone を経由する必要はありません。

### 前提

| 条件                                       | 補足                                                                                                 |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| Apple Watch Series 6 以降 / watchOS 9 以降 | 背景 BLE 起床の動作要件                                                                              |
| Watch が iPhone とペアリング済み           | Watch 単体では Xcode に出てきません                                                                  |
| **Mac / iPhone / Watch が同じ Wi-Fi**      | SSID だけでなく**バンド（2.4GHz / 5GHz）も揃える**こと。混在すると Xcode が Watch を見つけられません |
| Xcode に Apple ID でサインイン済み         | 無料の Apple ID（Personal Team）でも可。制限は下記                                                   |

### 手順

#### 1. 署名チームを設定する

このプロジェクトは `DEVELOPMENT_TEAM` が未設定です（`CODE_SIGN_STYLE = Automatic` のみ）。
Xcode で TuretetteWatch ターゲット → Signing & Capabilities → **Team** を選んでください。

Bundle ID が他と衝突する場合は `PRODUCT_BUNDLE_IDENTIFIER` を
`com.<自分の名前>.turetette.watch` などに変えます。

#### 2. iPhone のデベロッパモードを有効にする

設定 → プライバシーとセキュリティ → デベロッパモード → オン → 再起動。

#### 3. Apple Watch のデベロッパモードを有効にする

Watch の 設定 → プライバシーとセキュリティ → デベロッパモード → オン → 再起動 → 起動後にもう一度確認を求められるので承認。

> **項目が出てこない場合**（よくあります）
> iPhone をケーブルで Mac に繋ぎ、Xcode の Window → Devices and Simulators を開きます。
> iPhone の下に Watch が現れ、Watch 側に「このコンピュータを信頼しますか」が出るので信頼します。
> **その後で** Watch の設定を見るとデベロッパモードの項目が現れます。

#### 4. Xcode に Watch を認識させる

Window → Devices and Simulators。iPhone の下に Watch が並びます。
初回は「Preparing debugger support」でシンボルの準備が走ります。**数分〜十数分かかる**ので、
消えるまで待ってください。この間に Run しても失敗します。

#### 5. Run する

実行先を Apple Watch にして Run。初回インストールは遅いので、
**Watch を充電器に載せ、画面を点けたまま、Mac の近くに置いて**ください。

### このスパイク特有の注意 ★

#### (a) デバッガを繋いだままでは計測になりません

Xcode から Run するとデバッガが接続され、**アプリがサスペンドされません**。
それでは「背景で起きたか」を測れず、G0 の3つの問い全部が無意味になります。

インストール後は必ず **Xcode の Stop を押してデバッガを切り離し**、
Watch 側でアプリを起動し直してから計測を始めてください。

#### (b) アプリを開くと BLE の背景予算がリセットされます

Xcode からの起動も同じです。**計測の開始点は「最後にアプリを閉じた時刻」**になります。
インストール直後は一度アプリを開いて権限を許可し、フェーズを選び、
それから閉じて放置を始めてください。

#### (c) バックグラウンド更新をオンにする

Watch の 設定 → 一般 → App のバックグラウンド更新 で、本アプリがオンになっていること。
オフだと `WKApplicationRefreshBackgroundTask` が一切来ません。

#### (d) 無料 Apple ID を使う場合は7日で失効します

| 制限                                   | 値                          |
| -------------------------------------- | --------------------------- |
| プロビジョニングプロファイルの有効期間 | **7 日**                    |
| 同時に登録できる App ID                | 10 個（各 7 日で失効）      |
| 登録できるテストデバイス               | プラットフォームごとに 3 台 |

フェーズ A と B は日をまたいで分けるので、**7 日以内に収まるよう計画してください**。
失効するとアプリは黙って起動しなくなります。

### インストールに失敗したときの確認順

| 症状                                       | 対処                                                                                 |
| ------------------------------------------ | ------------------------------------------------------------------------------------ |
| Xcode に Watch が出てこない                | Wi-Fi のバンドを揃える / iPhone をケーブルで繋いで Devices and Simulators を開き直す |
| 「Preparing debugger support」が終わらない | Watch を充電器に載せて放置。初回は十数分かかることがある                             |
| **companion app が要る旨のエラー**         | `Info.plist` の `WKCompanionAppBundleIdentifier` を削除する（下記）                  |
| 署名エラー                                 | Team 未設定、または Bundle ID の衝突                                                 |
| 7 日後に起動しなくなった                   | 無料アカウントの失効。Xcode から入れ直す                                             |

> **`WKCompanionAppBundleIdentifier` について**
>
> 現在この値は `com.turetette` を指していますが、**その iOS アプリはまだ存在しません**。
> Info.plist のコメントにもあるとおり、シミュレータの検証を通すためだけに置かれた値です。
>
> watch 単独アプリではこのキーは**付けないのが正しい形**です。実機インストールが
> companion app 関連のエラーで失敗する場合は、このキーを削除してください。
>
> **P4（iPhone コンパニオン）で実際の Bundle ID を入れて復活させます。** 消したままにしないこと。

## 2.6. 実機接続のトラブルシュート記録（2026-08-31 / 2026-09-02）

実機接続でつまずいた 2 つの症状の記録。**同じ調査を繰り返さないために残す。**

| 日付       | 症状                                                        | 原因                               | 解決                                 |
| ---------- | ----------------------------------------------------------- | ---------------------------------- | ------------------------------------ |
| 2026-08-31 | Devices に**出てこない**                                    | Mac 側 CoreDevice のデーモン状態   | **Mac の再起動**                     |
| 2026-09-02 | 出るが **Connecting / Connected / Disconnected を繰り返す** | **Mac と Watch が別バンド・別 AP** | **両方を 2.4GHz の同一 AP に載せる** |

---

### 判明した機種と、その帰結 ★

| 項目       | 値                                                                 |
| ---------- | ------------------------------------------------------------------ |
| モデル番号 | **A2355 / MYF62J/A**                                               |
| 内部識別子 | `Watch5,11`                                                        |
| 機種       | **Apple Watch SE(第1世代)** GPS+Cellular 40mm（2020年、S5 チップ） |
| watchOS    | **10.6.2 が最終**（watchOS 11 で SE 第1世代のサポートが終了）      |

**この機種では G0-1 / G0-2 を測定できない。** 背景 BLE 起床の要件は「Apple Watch Series 6 以降」で、
SE(第1世代)は S5 世代 ── Apple が Series 4 / 5 と同時に切り捨てたグループに属する。

|                     | この機体で測れるか             |
| ------------------- | ------------------------------ |
| G0-1 背景 BLE 起床  | ❌ ハード要件を満たさない      |
| G0-2 予算の数え方   | ❌ 同上                        |
| G0-3 遡り問い合わせ | ⭕ 背景更新タスクで代用可能    |
| P1 の実機検証       | ⭕ 背景 BLE を使わないため可能 |

> **Series 6 以降の実機は、いずれ必ず必要になる。**

### 症状 1（2026-08-31）── Devices に出てこない

> ### 結論：Mac の再起動で解決した ★
>
> ネットワーク・ファイアウォール・バージョン・ロックはすべて無関係だった。
> **原因は Mac 側 CoreDevice のデーモン状態**で、再起動一発で Watch が Devices に現れ、
> Watch の 設定 → プライバシーとセキュリティ にデベロッパモードの項目も出現した。
>
> **同じ症状が出たら、長い切り分けをする前にまず Mac を再起動すること。**

#### 症状の詳細

- Watch は Wi-Fi 上に存在し、**ping に応答し、ポート 62078 も開いている**
- しかし **mDNS(Bonjour)には一切応答しない**
- そのため Xcode が発見できず、Watch の設定にデベロッパモードの項目も現れない

#### 循環依存（既知の問題）

```text
Xcode が Watch を認識できない  →  デベロッパモードの項目が出ない
            ↑                                    │
            └────────────────────────────────────┘
```

デベロッパモードは **Xcode が接続に成功して初めて**設定に現れる。
何度探しても見つからないのは正常な挙動であり、先に接続を成立させる必要がある。

#### 切り分けの結果 ── すべてシロだったもの

| 仮説                                       | 判定                                | 確認方法                                                                                                                               |
| ------------------------------------------ | ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| ネットワーク到達性                         | シロ                                | `ping 192.168.40.140` → 3/3 応答、`nc -z ... 62078` → open                                                                             |
| ルーターのアイソレーション                 | シロ                                | `ping6 fe80::...%en0` が双方向で成功                                                                                                   |
| IPv6 の不備                                | シロ                                | `networksetup -getinfo Wi-Fi`、`ifconfig en0` でグローバル/リンクローカル取得済み                                                      |
| Wi-Fi バンドの分離                         | シロ ／ **★ 症状 2 に対しては誤り** | リンクローカル ping が通る＝同一 L2。 **ただし「L2 が繋がる」ことと「デバッグトンネルが安定する」ことは別問題だった**（症状 2 を参照） |
| macOS ファイアウォール                     | シロ                                | `socketfilterfw --getglobalstate` → disabled                                                                                           |
| **ESET のファイアウォール**                | **シロ**                            | 一時停止した状態で再検証 → 変化なし                                                                                                    |
| iOS と watchOS の乖離                      | シロ                                | `~/Library/Developer/Xcode/*DeviceSupport/` の日付から、2026-04-08 に iOS 26.4 + watchOS 10.6.2 で接続成功していたことが判明           |
| Watch のロック                             | シロ                                | 手首装着（ロック解除維持）で再検証                                                                                                     |
| マルチキャストの遮断                       | シロ                                | iPhone の Bonjour 広告は en0 で受信できている                                                                                          |
| CoreDevice が iPhone 経由で Watch を見るか | **見ない**                          | `devicectl device info details` に Watch 関連の情報が一切無い                                                                          |

#### 使った調査コマンド

```bash
# Xcode から見えるデバイス
xcrun xctrace list devices
xcrun devicectl list devices

# Bonjour にペアリング用サービスが出ているか（Watch が出せば2件目が現れる）
dns-sd -B _remotepairing._tcp local
dns-sd -B _companion-link._tcp local

# Watch の IP を MAC から特定する（Watch の 設定→Wi-Fi に出る MAC を使う）
arp -an | grep -i "<Watch の MAC>"

# 到達性
ping <Watch の IP>
nc -z -G 2 <Watch の IP> 62078

# 過去に接続した実機の記録（機種と watchOS、日付が分かる）
ls -lT ~/Library/Developer/Xcode/watchOS\ DeviceSupport/
```

#### 解決までに試した順序（次回はこの順で）

1. **Mac の再起動** ← **これで解決した。最初にやること**
2. Xcode の Devices で iPhone を選び、詳細ペインの警告を読む（GUI にしか出ない情報がある）
3. Watch のペアリング解除 → 再ペアリング（**Watch が初期化される**。30〜60分）
4. **Series 6 以降の実機を用意する**（G0-1 / G0-2 にどのみち必要）

> この機体は G0-1 / G0-2 を測れないので、初期化してまで接続する価値は薄い。
> **P1 の実装を先に進め、実機検証は Series 6 以降の機体が入手できた時点でまとめて行う**のが合理的。

### 症状 2（2026-09-02）── Connected と Disconnected を繰り返す ★

Devices に Watch は出るが、`Connecting` のアニメーションのまま
**`Connected` になったり `Disconnected` になったりを繰り返す。**

> ### 結論：Mac と Watch を同じ 2.4GHz の AP に載せたら安定した ★
>
> **Apple Watch SE(第1世代) は 2.4GHz 専用**（Wi-Fi 4 / 802.11n 2.4GHz のみ）。
> Mac が 5GHz にいる限り、両者は**物理的に別の AP** に繋がる。

#### 実測した状態

```text
Mac (en0)      : ch 108 (5GHz, 80MHz, 802.11ac)   ← しかも DFS チャンネル(W56)
Apple Watch SE : 2.4GHz 専用。5GHz は掴めない
SSID           : 1 つで ch 1 / 6 (2.4GHz) と ch 44 / 48 / 108 / 124 (5GHz) に展開
                 → メッシュか複数 AP の構成
```

SSID が 1 つなので macOS の Wi-Fi メニューからバンドを選べない。
Mac と Watch の通信はバックホール経由になり、遅延とパケットロスが乗る。
**Xcode のデバッグトンネルはこれに耐えられない。**

加えて **ch 108 は DFS チャンネル**なので、レーダー検出で AP が突然
チャンネルを変えたり一時停波したりする。それ単体でも切断要因になる。

もう一つ、`_remotepairing._tcp` の**同一インスタンスが 3 経路**で見えていた。

```text
if 15 = en0   (Wi-Fi, 192.168.40.x)
if 16 = en11  (169.254.x ← 自己割り当て。構成に失敗した経路が生き残っている)
if 13 = en12  (UP だが IP 無し)
```

`en11` / `en12` は **iPhone を USB 接続すると生える**インターフェース。
CoreDevice がどの経路でトンネルを張るか迷い、切り替わるたびに再接続が走る。

#### 効いた手順（この 3 つをまとめて実施して安定した）

**(1) Mac と Watch を同じ 2.4GHz の AP に載せる** ← 本命

SSID が 1 つでバンドを選べないので、**iPhone のインターネット共有**を使うのが確実。

1. iPhone: 設定 → インターネット共有 → **「互換性を優先」をオン**（2.4GHz になる）
2. Mac と Watch の両方をそのホットスポットに接続
3. Xcode の Devices を開き直す

AP が 1 台になり、両方が同じ 2.4GHz 無線に載る。
メッシュのバックホールも DFS も経路から消える。
恒久的にやるならルーターに **2.4GHz 専用の SSID を切る**のが本筋。

##### (2) iPhone の USB を抜く

```bash
ifconfig -l | tr ' ' '\n' | grep -E "^en1[12]$"
```

出なくなれば経路が 1 本に絞れている。Watch は Wi-Fi 経由なので USB は要らない。

##### (3) Watch を「装着 + 設定→Wi-Fi 画面を開いたまま」にする

下の「Watch を接続可能な状態に保つコツ」の表のとおり。

> **3 つをまとめて実施したため、どれが決定打だったかは切り分けていない。**
> ただし (1) は Watch SE(第1世代)が 5GHz を掴めないという**ハード仕様に基づく**ので、
> 次回もまず (1) から試すのが妥当。

#### 効いたかの確認

```bash
xcrun devicectl list devices
```

State が `available (paired)` から **`connected`** に変わり、それが**維持される**のが成功。
`available (paired)` は「発見できているがトンネルが張れていない」状態。

経路が絞れたかは:

```bash
perl -e 'alarm 8; exec @ARGV' dns-sd -B _remotepairing._tcp local
```

同じインスタンス ID が複数の `if` に出なくなればよい。

#### それでも直らないとき

```bash
sudo pkill -9 remotepairingd remoted     # デーモンは自動で起き直る
```

これでも駄目なら Mac の再起動（症状 1 の結論）、最後に Xcode の Devices で Unpair → 再ペア。

#### 接続後 ── シンボルの取り込みで待たされる

`Copying shared cache symbols from ...` が出たら、**1GB 前後**を **2.4GHz 経由**で引いている。
**10〜40 分**かかる。パーセント表示が止まって見えても進んでいる。

| やってはいけないこと      | 理由                                   |
| ------------------------- | -------------------------------------- |
| Run する                  | 途中で走らせると失敗する               |
| Watch を手首から外す      | ロックされて接続が切れ、やり直しになる |
| 設定→Wi-Fi の画面を閉じる | Wi-Fi が眠る                           |
| ホットスポットを切る      | 経路が消える                           |

進捗の実態はここで見る（Xcode の表示より正確）。

```bash
du -sh ~/Library/Developer/Xcode/watchOS\ DeviceSupport/*/.tmp
```

**完了の合図**は `.copying_lock` が消え、`.tmp/` の中身が親フォルダ直下へ移ること。
これが済めば同じ watchOS 版に対しては二度と走らない。

> **既知の残骸**: 2026-04-08 に中断された取り込みの `.copying_lock` /
> `.processing_lock`（どちらも 0 バイト）が残っていた。症状 1 の時期に切れたもの。
> 取り込みが完走すれば解消する。完走しないまま繰り返す場合は
> `watchOS DeviceSupport/<機種> <版>/` ごと削除してやり直させる。

### Watch を接続可能な状態に保つコツ（両症状で共通）

装着とWi-Fi起動が両立しないという罠がある。

| 状態                                   | ロック                        | Wi-Fi                   |
| -------------------------------------- | ----------------------------- | ----------------------- |
| 充電器に載せる                         | ❌ 手首から外れてロックされる | ⭕ 起きている           |
| 手首に装着                             | ⭕ 解除が維持される           | ❌ Bluetooth 優先で眠る |
| **装着 + 設定→Wi-Fi 画面を開いたまま** | ⭕                            | ⭕                      |

最後の組み合わせだけが両立する。

## 3. 計測

### フェーズ A — notify だけで予算を使い切る（G0-1 と G0-2 の前半）

1. Watch でアプリを開き、状態タブで **フェーズ A** を選ぶ
2. Mac 側が「購読されました」と出るまで待つ（接続と notify 購読の完了）
3. Mac 側で `i` → `600`（10 分間隔）に設定する
4. **Watch のアプリを閉じ、手首から外して放置する**
   - アプリを開くと予算がリセットされるので、計測中は開かないこと
5. 2〜3 時間放置する
6. Watch でアプリを開き、集計タブを読む

#### 読み取り方（フェーズ A）

| 見るところ                             | 意味                                                            |
| -------------------------------------- | --------------------------------------------------------------- |
| 背景で受けた notify の件数             | **0 なら G0-1 は不成立。** 背景起床が来ていない                 |
| ログの `notify` 行の「取りこぼし=N」   | 送られたが届かなかった数。Mac 側 `s` の送信数と突き合わせる     |
| `budgetNear` / `budgetExceeded` の記録 | 何件目で予算が尽きたか。**5 件前後で止まるはず**                |
| `restore` の件数                       | OS がアプリを起こし直した回数。0 でなければ状態復元も効いている |

### フェーズ B — 切断だけで予算を使い切る（G0-2 の本題）

1. Watch でアプリを**開く**（これで予算がリセットされる）
2. 状態タブで **フェーズ B** を選ぶ
3. Mac 側で `i` → `3600`（1 時間間隔。notify で予算を消費させないため）
4. Watch のアプリを閉じ、放置する
5. **Mac 側で `d` を 10 分おきに 8 回ほど押す**（切断 → 自動再接続を繰り返させる）
6. Watch でアプリを開き、集計タブを読む

#### 読み取り方（フェーズ B）

| 結果                                                             | 結論                                                               |
| ---------------------------------------------------------------- | ------------------------------------------------------------------ |
| 背景での切断イベントが 5 件前後で止まり、`budgetExceeded` が出る | **切断起床も予算を消費する。** §6 の予算管理を厳しくする必要がある |
| 8 回すべて記録され、`budgetExceeded` が出ない                    | 予算は notify 起床だけを数えている。設計どおり                     |

### フェーズ C — `registerForConnectionEvents` は背景で発火するか（G0-5）★

**このフェーズだけは Series 6 未満の機体でも試せる可能性があります。**
背景 BLE 起床（`WKBluetoothAlertRefreshBackgroundTask`）とは別系統の API だからです。

```swift
// Watch 側。接続を保持していなくてもイベントが来るのが売り。
central.registerForConnectionEvents(options: [
    .peripheralUUIDs: [targetUUID]      // または .serviceUUIDs
])

func centralManager(_ c: CBCentralManager,
                    connectionEventDidOccur event: CBConnectionEvent,
                    for peripheral: CBPeripheral) {
    // event == .peerDisconnected をログに残す
}
```

1. Watch でアプリを開き、状態タブで **フェーズ C** を選ぶ
2. Mac 側で接続を確立させる
3. Watch のアプリを閉じ、放置する
4. **Mac 側で `d` を 10 分おきに 8 回ほど押す**
5. Watch でアプリを開き、集計タブを読む

#### 読み取り方（フェーズ C）

| 結果                                        | 結論                                                                |
| ------------------------------------------- | ------------------------------------------------------------------- |
| 背景で `.peerDisconnected` が記録されている | **★ 現機体でも切断検知が成立する。** G0-1 / G0-2 の保留を迂回できる |
| 前面のときしか記録されない                  | 背景起床の手段としては使えない。Series 6 以降を待つほかない         |
| 予算らしき上限で止まる                      | 何件目で止まったかを記録する（別枠の予算がある可能性）              |

> **第 1 回の途中経過（2026-09-02〜03）★**
>
> `[G0-5] 背景 55 件 / 前面 24 件、うち切断 38 件` ── **背景で発火することが確認できた。**
> `[G0-4] 試行 54 / 登録成功 54 / 失敗 0 / 実際に配信 48 件` ── **枠の中で通知を積めて、配信もされる。**
>
> 注意すべき点が 3 つある。
>
> 1. **意図した切断は 4 回なのに、切断イベントは 38 件。** 34 件は自然発生。
>    ただし **Mac と Watch の距離は 50cm** だったので、**§17.5 のレンジ境界では説明できない。**
>    治具側（Mac の BLE 電源管理・peripheral-sim の挙動）か、
>    watchOS が背景のアプリの BLE リンクを切っているかの切り分けが要る。
>    **Mac 側 `peripheral-sim` の接続/切断ログと件数を突き合わせれば分かる。**
> 2. **背景 55 件は §2.1 の「5 回/24h」を 10 倍以上超えている。**
>    この経路は背景 BLE 起床の予算とは別枠か、対象外に見える。別の上限があるかは未確認。
> 3. **`ts 版`の切断デリゲートが一度も呼ばれなかった**（ログは全て `旧版`）。
>    `connect` を `options: nil` で呼んでいたため、というのが仮説。§19.5-2 の訂正を参照。
>    第 2 回で `EnableAutoReconnect` を付けて再計測する。
>
> なお **試行 54 > 切断 38** なのは、通知プローブを `didDisconnect` と
> `connectionEventDidOccur` の**両方から呼んでいる**ため。二重計上なので、
> 「積めるか」の Yes/No には影響しないが、**成功率としては読めない。**

**計測中は notify を購読しません。** 購読したままだと、背景で来たイベントが
接続イベント経由なのか notify 起床経由なのか判別できなくなるためです。
画面でフェーズを C にすると購読の解除と `registerForConnectionEvents` の登録が同時に走ります。

> フェーズ C は `SpikeCentral.applyPhase()` が担当します。実装は
> `apple-watch/TuretetteWatch/TuretetteWatch/Spike/SpikeCentral.swift` を参照してください。

### G0-4 — 切断起床の枠でローカル通知を積めるか

**フェーズ B / C の計測中に自動で測られます。** 背景で切断を検知したその場で
ローカル通知の登録を試み、次の起床または前面化で**実際に配信されたか**を突き合わせます。

初回起動時に通知の許可を求められるので、**必ず許可してください。**拒否すると
「積めなかった」のか「許可が無かった」のか区別できなくなります。

#### 読み取り方（G0-4）

| 結果                       | 結論                                                              |
| -------------------------- | ----------------------------------------------------------------- |
| 登録成功 かつ 配信確認あり | **方式1 は成立する。** 切断起床の枠で発報できる                   |
| 登録成功だが配信確認なし   | 枠の中で `add` は通るが配信されない。**通知以外の発報手段が要る** |
| 登録失敗（`alertFail`）    | **方式1 は「再接続を試して黙る」だけになる。**設計の作り直し      |

あわせて、切断デリゲートの `timestamp` から
**「切断が起きた時刻」と「アプリが起きた時刻」の差**も記録されます（§19.5-2）。
P3 の遡及判定はこの遅延を前提に窓を決めるので、実測値が要ります。
ログの `disconnect` 行が `ts版` で始まっていれば timestamp 版が、
`旧版` で始まっていれば従来版が呼ばれています。

### G0-3 — 遡り問い合わせは実行枠に収まるか

フェーズ A / B の計測中に自動で測られます（起床のたびに 1 回）。
**歩数データが必要なので、計測中は Watch を装着して普通に歩いてください。**
手首から外して放置すると歩数が 0 になり、所要時間だけしか分かりません。

#### 読み取り方（G0-3）

| 見るところ                | 意味                                                   |
| ------------------------- | ------------------------------------------------------ |
| 開始 / 完了 / 未返却 の数 | **未返却が多ければ、背景実行枠で返っていない**         |
| 所要 中央値 / 最大        | §14.4 の仮定（GPS と違って枠内に返る）が正しいかの数字 |
| ログの `probeLost` 行     | 打ち切りか、次の起床まで返らなかったかが分かる         |

## 3.5. ログを Mac へ取り出す

Watch の中の `UserDefaults` は Mac から直接読めない。画面を書き写すのは現実的でないので、
**`os_log` にも同じものを流している**。Mac 側ではこう読む。

```bash
log stream --predicate 'subsystem == "com.turetette.watch.spike"'
```

Console.app でペアリング済みの Watch を選んでも同じものが見える。
過去ぶんをまとめて欲しいときは、集計タブの 2 つのボタンを押す。

| ボタン                  | 出るもの                                                 |
| ----------------------- | -------------------------------------------------------- |
| **集計を Mac へ**       | 集計タブの全文を 1 行ずつ                                |
| **全イベントを Mac へ** | 保存済みイベントを古い順に(時刻・種別・アプリ状態・詳細) |

`connEvent` の時刻がバーストか均等かは、後者を取れば Mac 側で数えられる。

> **注意**: `log stream` は流れているものだけを映す。ボタンを押す**前**に起動しておくこと。

## 6. 計測時の注意

- **Xcode のデバッガを繋いだままでは計測になりません**（§2.5-a）。Run したら必ず Stop で切り離すこと
- **アプリを開くと予算がリセットされます**（WWDC22）。計測中は開かないこと
- 24 時間のローリングウィンドウなので、フェーズ A と B は日をまたいで分けるのが確実
- Watch の「アプリのバックグラウンド更新」がオンになっていることを確認する
- 集計は直近 24 時間ぶんだけを対象にしています。それより古い記録はログタブで見てください
- Mac をスリープさせると広告が止まります。電源接続 + スリープ抑止（`caffeinate -s`）を推奨
